3.1 三维边界控制原则
一期坚持"2D 一张图为主入口、局部 3D 为增强视图"的原则。3D 用于事件研判、扩散推演、空间态势复盘和重点场景展示，不承担高频建档、规则配置、设备台账维护等操作。
 一期验收口径：2D 一张图完成日常业务主入口，3D 只做局部场景联动与占位接口。
 二期增强口径：在不重构一期底盘的前提下，扩展 3D 动态推演、综合指挥大屏和风险扩散仿真。
 前端约束：3D 渲染失败或性能不足时，不影响 2D 主业务链路。

4.2 SSO 与统一认证的高可用要求
 SSO 至少双实例部署，跨可用区或跨主机房；会话状态不得只保存在单机内存。
 Portal 与三平台对 SSO 的依赖必须有超时控制、重试上限和失败提示，不允许无限等待。
 应急旁路仅面向值班指挥人员开放，采用离线白名单账号或短期应急令牌；旁路权限默认只开放指挥必需能力，不开放高危配置能力。
 SSO 恢复后，应急旁路账号必须自动失效或人工回收，旁路期间的全部操作进入单独审计报表。
4.2.1 应急旁路安全细化要求
应急旁路是高风险但必要的韧性机制，只能在 SSO 故障、网络隔离、重大灾害或演练授权场景下启用，不得作为日常便捷登录方式使用。
1.应急令牌有效期
应急旁路账号或应急令牌默认短期有效；
单次签发有效期建议不超过 15 分钟，最长会话时长建议不超过 8 小时；
过期后必须自动失效，不允许静默续期；
若采用一次性应急码或离线令牌，使用后应立即作废，不得重复使用。
2.实物凭证管理
如采用应急 UKey、离线口令卡、纸质密封凭证或专用值班终端，必须执行"双人保管、领用登记、启封留痕、归还复核"机制；
凭证编号、持有人、启用时间、归还时间、使用原因必须纳入审计台账；
应急凭证不得长期由个人保管，不得拍照、转抄或通过即时通信工具传播。
3.权限最小化
应急旁路默认仅开放应急指挥必需功能，如事件查看、告警确认、派单、值班联络和态势浏览；
不开放高危配置能力，如权限管理、系统参数修改、模型发布、批量删除、主数据结构调整。
4.滥用检测机制
对应急旁路登录建立专项审计规则；
出现异常时间登录、异常地点登录、频繁启用、跨班组复用、短时间高频操作、批量导出等行为时，必须自动告警；
SSO 恢复后，系统应自动提醒关闭应急旁路，并对旁路期间所有操作生成单独审计报表。
5.启用审批与演练要求
生产启用必须有值班负责人或授权管理人确认；
演练启用必须区分"演练模式"与"真实故障模式"；
每次应急旁路启用后必须完成复盘，核查是否存在越权、滥用或凭证管理失控问题。
4.3 WebSocket、API Gateway 与数据加密基线
WebSocket 用于承载实时告警、工单状态推送、地图刷新事件和指挥态势更新，但其实时性不能以牺牲安全性和可控性为代价。Gateway、WebSocket 和数据加密要求应在一期即固化为基线。

4.3.1 WebSocket 连接安全要求
  1.   生产环境只允许使用 WSS，禁止明文 WS。 
  2.   WebSocket 升级前必须完成身份校验，校验信息可来自 OIDC 会话、短期访问令牌或网关签发的会话凭据。 
  3.   升级请求必须执行 Origin 白名单校验；对浏览器场景，需补充 CSRF Token 或等价防重放校验。 
  4.   服务端必须设置单用户连接数限制，默认建议每用户不超过 3 条并发连接；超限时拒绝新连接并记录审计。 
  5.   服务端必须设置消息体大小上限： 
     1.      客户端上行默认不超过 64 KB/帧； 
     2.      服务端下行默认不超过 256 KB/消息； 
     3.      超限消息直接拒绝并告警。 
  6.   必须启用心跳与僵尸连接清理机制： 
     1.      心跳间隔建议 30 秒； 
     2.      连续 90 秒无心跳或无有效交互则断开连接； 
     3.      断开原因应可追踪。 
  7.   上行消息必须有频率限制，防止恶意刷消息、订阅风暴或应用层 DoS。 
  8.   所有连接建立、断开、认证失败、超限、重连、补偿和异常关闭事件必须写审计日志。 
4.3.2 API Gateway 安全要求
API Gateway 作为统一入口，必须承担协议接入、鉴权、限流、审计、输入校验和基础攻击防护职责，不得仅作为简单转发层使用。
  1.   对外接口必须具备限流/配额控制，按用户、租户、来源 IP、客户端类型等维度限速； 
  2.   必须进行统一的参数校验、长度校验、格式校验和白名单校验； 
  3.   必须具备常见攻击防护能力，包括但不限于 SQL 注入、XSS、路径穿越、参数污染和异常大包拦截； 
  4.   对内高风险管理接口建议叠加 IP 白名单、堡垒机访问或专网访问约束； 
  5.   对关键写操作启用审计与风控，如批量导出、批量派单、权限修改、模型发布、主数据生效。 
4.3.3 数据传输与存储加密要求
  1.   平台内外通信默认启用 TLS 1.2+，关键链路优先采用更高版本与强加密套件； 
  2.   边缘节点到云端的数据上传必须加密传输，不得以"专线"或"内网"替代加密要求； 
  3.   对精确管网坐标、关键阀门状态、运维联系人、令牌、密钥材料等敏感字段，应采用静态加密、列级加密或等价防护机制； 
  4.   密钥、证书和加密材料不得直接写入代码、镜像或普通配置文件，必须纳入统一密钥管理体系； 
  5.   对训练导出数据、离线分析数据和备份文件，必须执行脱敏、加密和权限隔离。
4.4 权限矩阵与算法工程师数据访问边界
算法工程师默认不直接接触生产明细库；若确需排障或构建训练样本，必须走"审批 + 脱敏 + 时间窗授权 + 审计"四步流程。

7.2 数据质量评分框架
为防止异常告警由传感器故障、漂移、延迟、断点或脏数据触发，平台应在接入层和规则/模型层之间建立统一的数据质量评分机制。所有进入告警规则、推理流程和分析看板的数据都应附带 dq_score。
7.2.1 dq_score 计算公式
建议采用 100 分制质量评分，定义如下：
dq_score = 100 x (0.30xC + 0.25xV + 0.20xT + 0.15xK + 0.10xS)
其中：
  *   C：完整性（Completeness），取值 0~1，反映采样点是否缺失、字段是否齐全； 
  *   V：有效性（Validity），取值 0~1，反映是否落在合法量程、格式是否正确； 
  *   T：时效性（Timeliness），取值 0~1，反映采样与入库是否超时； 
  *   K：一致性（Consistency），取值 0~1，反映与邻近传感器、同拓扑对象或历史趋势是否一致； 
  *   S：稳定性（Stability），取值 0~1，反映是否存在平线、抖动异常、重复值、突变噪声等异常模式。 
若某一项缺失，则按最不利原则降权，不得简单按满分处理。
7.2.2 分值阈值
  *   A 级：dq_score >= 85数据质量高，可直接进入规则判定、模型推理和自动处置链路。 
  *   B 级：70 <= dq_score < 85数据质量可用，但需保留降权标记；重要事件仍可自动进入处置链路。 
  *   C 级：60 <= dq_score < 70数据质量降级，只允许进入"人工复核优先"链路；不建议直接触发高等级自动升级。 
  *   D 级：dq_score < 60数据不可靠，默认不直接触发正式管网事件，优先转为"数据质量异常/设备复核"告警。 
7.2.3 与告警置信度联动规则
建议将最终告警置信度定义为：
alarm_conf_final = alarm_conf_raw x (0.5 + 0.5 x dq_score / 100)
其中：
  *   alarm_conf_raw 为规则或模型原始置信度； 
  *   alarm_conf_final 为质量校正后的最终置信度。 
联动规则如下：
  1.   dq_score >= 85：原始置信度不降权； 
  2.   70 <= dq_score < 85：允许自动告警，但升级阈值提高一级； 
  3.   60 <= dq_score < 70：只允许进入人工确认或多源交叉校验流程； 
  4.   dq_score < 60：默认不自动生成正式事件，除非有多传感器、多规则或人工确认共同支撑。 
数据质量评分结果必须落库，供误报复盘、模型训练筛样、设备健康评估和报表统计使用。
7.3 传感器标定、漂移与检修闭环
 每个传感器必须维护标定版本、标定日期、有效期、标定人员、参考标准、修正参数。
 到期前自动生成提醒；逾期未标定的设备，告警结果默认降权并纳入设备健康看板。
 当标定参数发生变化时，历史数据默认不覆盖原始值；通过"校正视图"提供追溯修正结果，避免直接篡改原始采样。
 若判定为漂移而非真实异常，系统应自动创建"检修/复核"工单，而不是直接升级为管网事件。
7.4 坐标系、投影与 Z 轴深度标准
本版建议采用"内部权威坐标 + 外部展示坐标"的双坐标体系：内部权威存储采用项目所在地区统一的工程投影坐标（建议以 CGCS2000 投影或业主已批复的地方坐标为准）；外部互联网底图展示可转换为 WGS84/Web Mercator。
 空间库至少同时保存 authority_srid、display_srid、geometry_2d、z_top、z_bottom、bury_depth、elevation_ref 等字段。
 坐标转换服务必须统一封装，不允许前端、ETL、导入工具各自私算。
 Z 轴采用米为单位，明确是"相对地面埋深"还是"绝对高程"，并在字段说明中写死。
 导入第三方资料时，必须在入库前登记坐标系来源、转换参数与精度等级。

7.5.1 ST-GNN 冷启动与区域相似性迁移策略
ST-GNN 依赖拓扑结构、时序特征和历史事件样本。对于新增区域、历史样本不足区域或主数据大规模变更后的区域，禁止直接按成熟区域同等置信度上线。
冷启动阶段建议采用"相似区域迁移 + 影子运行 + 分阶段放权"机制。
（1）区域相似性定义
建议建立区域相似性分数 sim_region，用于判断新区域可参考哪个已成熟区域的模型参数或初始化权重：
sim_region = 0.40xTopo + 0.30xHydro + 0.20xAsset + 0.10xEnv
其中：
  *   Topo：拓扑结构相似度，如节点度分布、管段长度分布、环网/枝网特征； 
  *   Hydro：水力/运行特征相似度，如压力波动、流量周期性、夜间基线； 
  *   Asset：资产属性相似度，如材质、口径、埋深、服役年限； 
  *   Env：环境相似度，如地层、道路荷载、施工扰动、气象条件。 
仅当 sim_region 达到预设阈值时，才允许复用相似区域模型作为冷启动初始模型。
（2）冷启动阶段控制规则
  1.   新区域上线前先运行影子模式，不直接触发自动派单； 
  2.   冷启动期建议不少于 30 天，期间模型输出仅作为辅助研判信息； 
  3.   冷启动期内模型告警置信度上限建议封顶，例如不超过 0.60； 
  4.   只有在样本量、稳定性和误报率满足门槛后，方可进入正式联动。 
（3）主数据变更后的再训练要求
当管段、节点、拓扑关系发生分裂、合并、重编码或批量调整时，应评估 ST-GNN 图结构是否发生显著变化。达到阈值时必须触发以下动作之一：
  1.   全量再训练； 
  2.   局部图增量训练； 
  3.   进入降级模式，仅保留规则兜底与人工复核。 
主数据版本、特征版本和模型版本必须绑定，避免出现"主数据已变、模型仍按旧拓扑运行"的隐性风险。
8. 可靠性、运维与部署工程化
8.1 告警事件化、跨服务一致性与幂等
"告警 --> 事件 --> 工单 --> 通知"跨越多个服务，必须以最终一致性为设计前提，而不是默认依赖跨库事务。建议采用"本地事务 + Outbox + 事件驱动 + 幂等键"的模式；如存在复杂回滚链路，可增加 Saga 编排器。
 告警事件化服务在同一事务中同时写业务表和 outbox_event 表；消息投递成功后再更新投递状态。
 工单创建幂等键建议固定为 incident_id + action_type + version；重复消费不得生成重复工单。
 通知服务只消费"工单已生成/已派单/已升级"等稳定事件，失败重试超过阈值后进入死信队列。
 任何阶段失败都必须可追溯到 trace_id、message_id、retry_count 和最后错误原因。

8.1.1 Outbox Relay 组件方案
为降低业务服务直接向消息中间件发送消息时的失败分叉问题，建议引入独立的 Outbox Relay 组件。业务服务在本地事务中同时写入业务表与 outbox_event 表；Relay 组件再异步读取 outbox_event 并投递到消息总线。
建议 outbox_event 至少包含以下字段：event_id、aggregate_type、aggregate_id、event_type、payload、trace_id、status、retry_count、next_retry_time、created_at、sent_at、last_error。
Relay 处理状态建议定义为：
  *   NEW：待发送； 
  *   SENDING：已被某个 Relay 实例认领； 
  *   SENT：已成功发送； 
  *   FAILED：发送失败待重试； 
  *   DEAD：超过重试上限，转人工处理。 
多实例 Relay 应采用"分片扫描 + 批量认领 + 跳过已锁记录"的机制，避免重复发送和热点竞争。
8.1.2 Outbox 表清理与归档策略
为避免 outbox_event 表无限膨胀，必须设计清理策略：
  1.   SENT 事件在热表中建议保留 7~30 天； 
  2.   超期成功事件转归档表或对象存储； 
  3.   DEAD 事件必须长期保留到问题闭环，不得自动物理删除； 
  4.   清理任务与归档任务必须可观测，禁止后台静默执行且无失败告警； 
  5.   归档后仍需保留按 trace_id、event_id 查询历史链路的能力。 
8.1.3 事务型消息备选方案对比
若基础设施支持事务型消息，也可将"本地事务 + Outbox"与"事务型消息"做备选对比。
  *   Outbox 方案优点：与数据库和消息中间件解耦，审计链完整，适合异构系统；失败可追踪、可补偿。 
  *   Outbox 方案缺点：需要额外 Relay 组件、状态管理和表清理策略，实现复杂度较高。 
  *   事务型消息方案优点：业务链相对简洁，发送与提交的一致性更直接。 
  *   事务型消息方案缺点：对中间件能力依赖更强，跨多语言、多数据库或跨服务场景下适配复杂；审计追踪往往不如 Outbox 明确。 
若一期团队更重视可审计、可补偿和跨系统兼容性，默认优先推荐 Outbox；若基础设施已统一且事务型消息能力成熟，可作为专项评审后的备选方案。
8.2 Gateway、关键依赖与 WebSocket 的韧性设计
 API Gateway / BFF 至少双实例；对 GIS、主数据中心、告警引擎、模型网关等关键依赖统一配置超时、重试上限、熔断和隔仓。
 熔断后必须返回可解释降级结果，例如"仅展示缓存快照""仅展示 2D""仅走规则告警链"。
 WebSocket 网关与业务服务解耦，连接态保存在可共享存储中；单实例故障时客户端通过自动重连与未确认序号补偿恢复。
 关键读链路可走缓存/快照，关键写链路优先保证事件、工单与审计不丢失。
8.2.1 WebSocket 序号补偿边界
为支持断线重连后的消息补偿，WebSocket 服务端应按"时间窗 + 条数窗"双重限制保留可补偿消息，不得无限缓存。
建议默认配置如下：
  1.   告警/工单/事件类频道：保留最近 2 小时且不超过 20,000 条消息； 
  2.   地图刷新/看板状态类频道：保留最近 30 分钟且不超过 10,000 条消息； 
  3.   关键频道可按租户和业务域单独配置，但必须有上限，不得无限制扩大。 
客户端每次连接或重连时应上报 last_ack_seq，服务端根据该序号判断是否可以增量补偿。
8.2.2 超窗处理策略
若客户端请求补偿的起始序号已超出服务端保留窗口，则不得伪装成"已完全补齐"。必须执行以下策略：
  1.   服务端返回"已超出补偿窗口"标记； 
  2.   客户端转为走 REST/BFF 快照接口重新拉取当前状态； 
  3.   快照完成后，以新的序号重新建立实时订阅； 
  4.   审计日志中记录超窗次数、频道、终端和时长，用于分析网络质量或客户端稳定性问题。 
对于超窗场景，系统应保证"最终状态正确"，即使无法保证"中间每条消息都重放"。

8.3 可观测性与 Runbook
可观测性不是"有监控图表"即可，而是要支撑故障快速定位、值班处置、升级决策和事后复盘。除指标、日志、链路追踪外，必须同步建设可执行的 Runbook。
8.3.1 可观测性自身高可用要求
  1.   Prometheus、日志系统、链路追踪系统和告警通道不得与核心业务完全同机部署； 
  2.   观测系统建议采用独立节点池、独立存储或独立命名空间，避免业务故障时观测能力同时失效； 
  3.   监控采集失败、日志积压、追踪链路中断本身也必须有告警； 
  4.   关键业务 SLI、SLO、错误预算和容量趋势必须可报表化输出。 
8.3.2 Runbook 文档结构
每一类高频故障都应有独立 Runbook，至少包含以下字段：
  1.   故障名称； 
  2.   触发条件与监控告警名称； 
  3.   影响范围判断方法； 
  4.   首次响应动作； 
  5.   诊断步骤； 
  6.   临时止血方案； 
  7.   根因定位路径； 
  8.   恢复验证步骤； 
  9.   升级联系人与升级条件； 
  10.   复盘输出要求。 
8.3.3 一期必须具备的 Runbook 列表
一期建议至少完成以下 Runbook：
  1.   SSO 不可用或认证异常； 
  2.   WebSocket 大面积断连； 
  3.   边缘节点批量离线； 
  4.   时序写入堆积或入库延迟突增； 
  5.   告警风暴/误报风暴； 
  6.   工单通知通道失败； 
  7.   主数据发布失败或空间变更冲突； 
  8.   模型推理超时或回退规则失效； 
  9.   数据质量评分大面积下降； 
  10.   备份恢复演练失败。 
8.3.4 值班与演练要求
Runbook 不得停留在文档层。必须建立值班响应流程、升级规则和演练计划：
  1.   明确一线值班、二线研发、三线架构/平台负责人； 
  2.   明确升级时限和升级触发条件； 
  3.   每季度至少开展一次高可用或恢复类演练； 
  4.   每次重大故障后必须更新对应 Runbook。 
8.4 配置、密钥、容器化与发布
8.4.1 CI/CD 测试与发布门禁要求
CI/CD 不仅负责自动构建和部署，还必须承担质量门禁和变更风险控制职责。建议最低门禁如下：
  1.   测试覆盖率要求 
     1.      后端单元测试覆盖率建议不低于 70%； 
     2.      告警、工单、权限、主数据、数据接入等核心域建议不低于 80%； 
     3.      前端核心组件与状态管理测试建议不低于 60%； 
     4.      关键业务流程必须具备 E2E 用例，如登录、告警确认、工单流转、地图联动、模型回退。 
  2.   安全扫描门禁 
     1.      必须执行 SAST、依赖漏洞扫描、镜像漏洞扫描和 IaC/配置扫描； 
     2.      高危漏洞默认阻断发布，中危漏洞需明确豁免流程和整改期限； 
     3.      涉及密钥泄露、硬编码口令、越权缺陷、严重注入风险的构建直接失败。 
  3.   数据库迁移脚本规范 
     1.      所有 DDL/DML 变更必须走版本化迁移脚本，不允许线上手工改库代替正式变更； 
     2.      脚本必须可追踪、可回放、可审计； 
     3.      发布前必须在测试环境和预发布环境验证迁移耗时、锁表风险和回滚方案； 
     4.      对大表结构变更应优先采用在线迁移、灰度变更或双写过渡方案。 
  4.   发布策略 
     1.      核心服务支持滚动发布、蓝绿发布或灰度发布； 
     2.      发布失败必须支持一键回滚； 
     3.      关键指标异常时自动中止继续发布。 
 服务配置采用集中配置中心或等价方案统一管理；环境变量只承载极少量启动参数，不承载敏感密钥。
 数据库密码、API Key、OIDC Client Secret、证书材料必须纳入 Vault 或等价 KMS/Secret 管理服务，严禁写入镜像、仓库或明文配置。
 部署建议采用容器化 + Kubernetes；核心服务支持滚动升级、蓝绿或灰度发布，支持一键回滚。
 基础设施资源、网络、存储、证书和监控建议纳入 IaC，至少做到可重复部署、可审计和可回放。
8.5 高可用部署与发布示意
部署架构应同时满足高可用、可扩展、可观测、可回滚和安全隔离五类要求。建议采用"多实例服务层 + 独立状态层 + 独立观测层 + 统一密钥管理"的总体部署思路。
8.5.1 核心部署要求
  1.   入口层 
     1.      Ingress/Gateway 至少双实例部署； 
     2.      入口层支持限流、熔断、TLS 终止和灰度路由。 
  2.   业务服务层 
     1.      SSO、Portal、综合管理平台、应急指挥平台、智能诊断中枢及支撑服务均采用多实例部署； 
     2.      核心服务跨可用区分布； 
     3.      服务之间通过服务发现和网关策略通信。 
  3.   状态与中间件层 
     1.      业务数据库采用主备、高可用集群或等价方案； 
     2.      TSDB、消息总线、Redis、对象存储必须按高可用部署； 
     3.      Outbox、审计日志和工单数据需独立保留，不与缓存同生命周期。 
  4.   观测与安全层 
     1.      Prometheus、日志、Tracing、审计平台、Vault/KMS 单独部署并与业务层逻辑隔离； 
     2.      堡垒机、漏洞扫描、镜像仓库和发布系统纳入运维安全域。 
  5.   发布与回滚层 
     1.      发布流水线与生产运行面分离； 
     2.      灰度发布期间支持新旧版本并行； 
     3.      配置中心、Secret 管理和镜像版本应可追溯到每一次发布批次。 
8.5.2 生产环境建议最小拓扑
生产环境至少应具备：
  *   双可用区或双机房入口； 
  *   双实例以上 SSO/Gateway/BFF； 
  *   核心业务服务多副本； 
  *   高可用数据库与高可用 TSDB； 
  *   独立消息总线； 
  *   独立对象存储与备份存储； 
  *   独立观测系统与告警通道； 
  *   独立密钥管理与镜像仓库。

审查报告指出"未指定项过多"会导致设计方案在实施阶段失去约束力。为避免后续前后端拆分、采购选型、部署实施和验收时反复争议，本章将关键事项分为"已确认"和"尚未确认"两类管理。
9.1 已确认事项
以下事项在本版中视为已确认，不再反复摇摆：
  1.   总入口口径固定为"SSO --> Portal --> 综合管理平台 / 应急指挥平台 / 智能诊断中枢"； 
  2.   一期以 2D 一张图为主入口，局部 3D 为增强视图； 
  3.   一期完成基础底盘、全模块展示与关键链路贯通，二期接入算法与三维增强； 
  4.   所有业务结果必须落到 segment_id 或 node_id； 
  5.   告警、事件、工单和通知链路按最终一致性设计； 
  6.   统一采用可审计、可补偿、可回退的工程化路线，不接受"先上线、后补治理"。

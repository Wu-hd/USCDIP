   地下管网数字化健康监测系统
一期前后端任务拆分汇总
基于《地下管网一体化监测运维与应急指挥平台工程级设计方案（审查修订版 V3）》整理
适用于前后端分离开发、任务拆分、迭代排期与 VS Code Copilot Pro 协同编码
                                 文档定位
把方案要求转换为可独立开发、可测试的小任务列表
适用阶段
一期详细设计、前后端拆分、研发排期、联调准备
任务粒度
单任务建议控制在 30 分钟 -- 2 小时
建议使用方式
先冻结前置约束，再按前端 / 后端并行推进，最后做闭环联调
一、方案核心结论
 :: 一期不是"页面集合"，而是后续二期不能推翻重做的工程骨架。
 :: 对外统一口径固定为：SSO --> Portal --> 综合管理平台 / 应急指挥平台 / 智能诊断中枢；平台支撑层仅作为工程底座，不作为第四入口。
 :: GIS 以"2D 一张图"为主入口，3D 仅作为局部增强视图；3D 失败不能影响 2D 主链路。
 :: 一期必须打通"资产 / GIS --> 设备接入 --> 时序存储 --> 实时监测 --> 告警 --> 事件 --> 工单 --> 回写"的完整闭环。
 :: 算法模型一期可以预留接口，但模型治理框架必须先做：注册、版本、灰度、回退、审计、规则兜底都要留位。
二、任务拆分原则
 :: 每个任务应有明确输入、输出与验收口径，避免"做一半才发现边界不清"。
 :: 前后端共享字段命名、状态机、错误码、权限边界、坐标口径，不允许各自定义。
 :: 优先拆"骨架类任务"：认证、主数据、对象链、GIS 主入口、告警事件工单闭环、时序链路与审计埋点。
 :: 每个任务同时写出易漏细节，防止后期返工；每个任务附一句 Copilot 提示词，便于快速出代码框架。

六、最容易忽略的设计细节（建议在评审时逐条过）
 :: Portal 不能承载业务编辑页面，否则边界会迅速漂移。
 :: 2D 是一期主入口，3D 只做增强与占位；3D 失效不能拖垮日常业务。
 :: 坐标与深度字段必须统一，不允许前端、导入程序、后端各自换算。
 :: 事件、工单、模型结果都必须落到对象链主键，否则后续 GIS 联动和追溯会断链。
 :: 告警不等于事件，事件不等于工单；三者必须有清晰状态机与转换规则。
 :: WebSocket 不能只做"收到就展示"，必须实现心跳、重连、ack、补发与去重。
 :: Refresh Token 轮换下，前端与后端都要处理并发刷新问题。
 :: 在线数据与补偿数据必须双口径展示，不能混成一条 SLA 统计线。
 :: 数据质量不只是展示分数，它还会影响规则告警与人工复核策略。
 :: 算法工程师默认只能看脱敏特征视图，不能直接查生产明细与精确坐标。
 :: 工单与通知消费必须有幂等键和死信处理，否则很容易重复派单。
 :: trace_id、event_time、recv_time 如果不在一期打通，后续很难再补全。
